# 推荐页优化 · 需求提案

> 状态：**待确认**（本文件只提需求，未改任何代码）
> 日期：2026-10-13
> 依据：通读 `src/store/useAppStore.ts`、`src/lib/recommend.ts`、`src/lib/pantry.ts`、
> `src/screens/HomeScreen.tsx`、`src/screens/RecipesScreen.tsx`、`src/components/FilterSheet.tsx`，
> 并用真实菜谱数据（103 道 / 611 条食材）跑过验证脚本。文中每个数字都是实测。

## 零、先说结论

现在的"推荐"其实**不是推荐，是随机**：它在"当前分类 + 忌口"过滤后，从剩下的菜里
`Math.random()` 挑一个。首页那张卡片既不认识你的口味，也不认识你的做饭记录，
更不是"今日"的。

按严重程度，我把它拆成 4 组需求：

| 组 | 问题 | 严重度 | 建议 |
| --- | --- | --- | --- |
| A | 忌口**挡不住**牛肉，会推荐给不吃牛肉的人 | **P0 正确性** | 必须修 |
| B | 忌口被"安全兜底"**静默架空** | **P0 正确性** | 必须修 |
| C | 口味偏好是个**摆设**，点了没反应 | P1 功能 | 建议做 |
| D | 首页不是"今日"，"最近很受欢迎"也不"最近" | P1 体验 | 建议做 |
| E | 已有数据（做饭评分、用时、库存保质期）**完全没进推荐** | P2 增强 | 可选 |

## A 组：忌口挡不住（P0，正确性 bug）

### A1. 「不吃牛肉」形同虚设

实测：`AVOID_OPTIONS` 里的 `牛肉`、`羊肉`、`内脏` 三项，**挡掉的菜数 = 0**。

原因在 `useAppStore.ts:143` 的匹配方式：

```ts
ing.name.includes(bad) || bad.includes(ing.name)
```

食材表里根本没有"牛肉"这个词，写的是 **`牛腩` / `牛里脊`**：

| 忌口项 | 数据里的实际食材 | 当前能否挡住 |
| --- | --- | --- |
| 牛肉 | `牛腩`、`牛里脊` | **0 道** ❌ |
| 羊肉 | （菜谱里没有羊肉菜） | 0 道（无害但无用） |
| 内脏 | `猪肝`、`百叶` | **0 道** ❌ |

**影响**：用户勾了"不吃牛肉"，首页照样把「红烧牛肉面牛肉」「西红柿炖牛腩」推给他。
10 道牛肉菜一道都没挡住。这不是体验问题，是**功能失效**。

**需求**：忌口匹配要能识别"牛肉 ⊃ 牛腩/牛里脊"这类上下位关系。
建议在 `constants.ts` 里给每个忌口项配一组同义词/子串，而不是靠字符串互含硬猜：

```ts
export const AVOID_GROUPS: Record<string, string[]> = {
  牛肉: ['牛腩', '牛里脊', '牛', '肥牛'],
  内脏: ['猪肝', '百叶', '肥肠', '腰花', '胗', '肚'],
  羊肉: ['羊', '羊排', '羊腿'],
  虾: ['虾', '虾仁', '虾皮'],
  // …
};
```

### A2. 忌口会误伤无关的菜

反向问题：子串互含也会**错杀**。实测：

| 忌口 | 被连带挡掉 | 道数 | 是否合理 |
| --- | --- | --- | --- |
| 葱 | `洋葱` | 7 道（洋葱炒肉、黑椒牛柳、孜然牛肉、咖喱鸡…） | ❌ 洋葱和葱是两种东西 |
| 蒜 | `蒜苔` | 1 道（蒜苔炒肉） | ❌ 蒜苔是菜不是调味 |
| 虾 | `虾皮` | 1 道（紫菜蛋花汤） | ⚠️ 可争议，虾皮确实是虾制品 |

**需求**：忌口匹配要么走 A1 的显式分组，要么至少把"洋葱/蒜苔"这类列入白名单排除。
**这条要和 A1 一起做**——同一处代码，改一次解决两个方向的问题。

## B 组：忌口被静默架空（P0，正确性）

### B1. 过滤到空就"偷偷放行"

`useAppStore.ts:157`：

```ts
const safe = pool.filter((dish) => !hitsAvoid(dish, avoid));
pool = safe.length > 0 ? safe : pool;   // ← 空了就退回未过滤的池子
```

`RecipesScreen.tsx:60` 有一份**完全相同**的复制粘贴。

实测触发场景：

| 忌口 | 分类 | 结果 |
| --- | --- | --- |
| 辣椒 | 素菜/豆类 | safe=0 → 回退，仍推荐含辣椒的菜 |
| 葱 | 主食类 | safe=0 → 回退，仍推荐含葱的菜 |
| 蒜 | 素菜/豆类 | safe=0 → 回退，仍推荐含蒜的菜 |

**影响**：对"不爱吃"的人这是体验问题；对**过敏**的人这是安全问题。
而且它**静默发生**，用户完全不知道自己的忌口被绕过了。

**需求**：二选一（我建议前者）：

- **方案 1（推荐）**：回退时**不要静默**。明确告诉用户"这个分类下没有符合忌口的菜"，
  给一个空状态 + "查看全部"按钮，让用户自己决定要不要放宽。忌口是硬约束，不该被代码偷偷推翻。
- **方案 2**：允许回退，但界面上必须显示"已忽略忌口"的提示条。

### B2. 两处重复实现

`useAppStore.ts` 的 `hitsAvoid` 和 `RecipesScreen.tsx` 里的内联版本是**两份逻辑**，
A1/A2 的 bug 也是**两份**。改的时候必须一起改，否则首页修好了菜谱页还是坏的。

**需求**：抽成一个共用函数（`lib/avoid.ts`），两处都调它。

## C 组：口味偏好是摆设（P1）

### C1. 六个口味标签，一个都不生效

`FilterSheet` 里"口味偏好"给了 6 个标签：`少油 / 少盐 / 微辣 / 不吃辣 / 偏甜 / 重口味`。

实测：
- `tasteTags` 在 store 里**只被存和读**（`useAppStore.ts:421`），
  **推荐和筛选逻辑一次都没引用过**。
- 菜谱数据里**没有任何一道菜**带这些标签——`tags` 字段的全部取值只有 12 种：
  `快手`(58)、`慢炖`(13)，以及 10 个**分类名**。口味覆盖率 = **0/103**。

也就是说：用户勾"不吃辣"，**什么都不会发生**。

**需求**：两条路，请选一条：

- **方案 A（诚实，成本低）**：既然数据不支持，就把这组 UI 先摘掉或置灰标注"即将支持"，
  别让用户以为点了有用。
- **方案 B（真做，成本中）**：给菜谱数据补口味属性。注意 `dishes.ts` **不能手改**
  （由 Excel 生成），所以要么改 `work/extract-dishes.py` 的生成规则从步骤/食材反推，
  要么新增一份 `taste-overrides.json` 人工标注，再让 `wire-dish-covers.mjs` 那一步合并进去。
  然后 `recommendPool` 里按 `tasteTags` 加权/过滤。

> 我的建议：**先做方案 A**，等确定真的要这个功能再做 B。
> 因为"不吃辣"其实**已经被忌口里的「辣椒」覆盖了**（能挡 28 道），功能是重叠的。

## D 组：首页不是"今日"（P1，体验）

### D1. 「今日家常菜」这个 badge 名不副实

`currentDishId` 是**持久化**的，只在三种情况变：用户点「换一个试试」、切分类、当前菜被删。

**没有按天轮换的逻辑。** 后果：

- **所有人第一次打开，看到的都是「红烧肉」**（`initialState` 里 `currentDishId: DISHES[0].id`）。
- 之后只要用户不主动点，这张卡**可以几周不变**，但徽章一直写着"今日家常菜"。

**需求**：要么让"今日"名副其实，要么把文案改成"为你推荐"。

若要做真·今日推荐，建议用**日期做种子**而不是纯随机：

```
seed = hash(YYYY-MM-DD)          // 同一天内稳定
dish = pool[seed % pool.length]  // 换天必换菜
```

好处：同一天反复进出 App 看到的是同一道（不像现在每次冷启动可能跳），
第二天自动换新，且不需要服务器。

### D2. 「最近很受欢迎」永远不变

`HomeScreen.tsx:40-47` 按 `popularity` 静态排序取前 6，只排除当前菜。
`popularity` 是**写死在菜谱数据里**的常量（55~95，103 道菜只有 38 个不同值）。

所以这 6 道菜**永远**是同样 6 道，"最近"二字是假的。

**需求**：三选一（按推荐度）：

1. **改名**成「大家都爱做」/「人气菜谱」——最省事，也最诚实。
2. **换成真·个性化**：改用用户的 `favorites` + `logs`（做饭记录）来算，
   这样它就是"你的常做菜"，会随使用变化。
3. **加时间维度**：结合 `logs` 里最近 30 天的记录做"最近"。

> 建议 1 + 2 组合：标题改「你常做的菜」，有记录时按记录排，没记录时退回人气榜。

### D3. 首页的"换一个"与收藏的关系可能是反的

`nextDish` 的优先级是：

```
① 没看过 + 非收藏 + 家里食材对得上
② 没看过 + 非收藏
③ 没看过（收藏也行）
④ 没看过且非收藏的兜底
⑤ 兜底
```

**收藏的菜被系统性地排到最后**。但收藏恰恰代表"我喜欢这道"。

**需求**：请确认这是有意设计还是副作用。
如果本意是"别老推同一道"，那正确做法是**排除最近 N 次已推过的**，
而不是排除"我喜欢的"。建议把收藏从惩罚项改成**小加权**。

## E 组：已有数据没进推荐（P2，增强）

这几条是"手上明明有牌却没打"：

### E1. 做饭评分完全没用上

`logs` 里有 `rating: 1~5`（`LogSheet` 让用户打星）。**推荐逻辑一次都没读 `logs`。**

后果：用户给某道菜打了 **1 星**（不喜欢），它照样会被推荐，甚至可能连着推。

**需求**：低分菜降权或拉黑。这是**投入产出比最高**的一条——
数据已经有了，用户也已经在录了，只差把它接进算法。

### E2. 用时没进推荐

数据很完整：**37 道 ≤15 分钟**、39 道 16~30 分、21 道 31~60 分、6 道 >60 分。

**需求**：加"今天想快点吃"的入口（或按时段自动判断：工作日中午偏向快手菜），
按 `minutes` 过滤/加权。

### E3. 库存和保质期没联动

`pantryExpiry` 已经能算出"快过期"的食材，`IngredientsScreen` 也已经在用
`cookableDishes` 排序。但**首页推荐完全不看库存**。

**需求**：优先推荐"能用掉快过期食材"的菜。这对"买菜页 + 冰箱"这条主线是自然闭环，
也直接减少浪费。属于锦上添花，放最后做。

### E4. `recommendPool` 有个死参数

`useAppStore.ts:364` 调用时第三个参数恒为 `[]`：

```ts
recommendPool(activeCategory, avoid, [], allDishesOf(state))
```

导致 `recommendPool` 内部那段 `hasPantry` 分支**永远不会执行**（死代码）。
`nextDish` 自己在第 376 行另算了一遍 `matched`。

**需求**：清掉死参数，或统一到一处。纯代码卫生，顺手做。

## 建议的实施顺序

按"用户能感知的价值 ÷ 成本"排：

| 顺序 | 内容 | 理由 |
| --- | --- | --- |
| 1 | **A1 + A2 + B1 + B2** | 正确性 bug，必须修；一次改完共用函数 |
| 2 | **E1**（评分进推荐） | 数据现成，收益直接 |
| 3 | **D1**（真·今日推荐） | 首页观感立刻不同，成本低（日期种子） |
| 4 | **D2**（标题改名或个性化） | 先改名止损，有精力再个性化 |
| 5 | **C1 方案 A**（摘掉或标注口味 UI） | 消除"点了没反应"的困惑 |
| 6 | D3 / E2 / E3 / E4 | 需要你拍板设计意图或属于增强 |

## 需要你拍板的 5 个问题

1. **忌口过滤到空时**：宁可给空状态（安全），还是允许回退但要提示？
2. **口味偏好**：先摘掉 UI（方案 A），还是投入补数据真做（方案 B）？
3. **首页"今日推荐"**：要做成按天轮换吗？还是把文案改成"为你推荐"？
4. **收藏的菜**：该被降权（现状）还是加权？现在的逻辑是把收藏排到最后。
5. **「最近很受欢迎」**：只改名，还是换成基于你做饭记录的"常做菜"？

# 实施记录（A / B / C 组已落地）

> 2026-02 完成。以下记录实际改法和验证结果，后续改动请以此为准。

## 已确认的决定

| 问题 | 决定 |
| --- | --- |
| 1. 忌口过滤到空 | **方案 1**：空状态 +「查看全部」，不回退 |

## A 组：忌口真的生效了

新增 `src/lib/avoid.ts` 作为**唯一**实现，`src/constants.ts` 增加两张表：

- `AVOID_GROUPS`：一个忌口项对应哪些食材写法。
- `AVOID_EXCEPTIONS`：名字带那个字但其实是别的东西的食材。

修好的三类问题：

| 问题 | 修前 | 修后 |
| --- | --- | --- |
| 忌口「牛肉」挡 0 道 | 0 道 | **10 道** |
| 忌口「内脏」挡 0 道 | 0 道 | **2 道** |
| 忌口「葱」误伤洋葱 | 误伤 | 不误伤（挡 43 道） |
| 忌口「蒜」误伤蒜苔 | 误伤 | 不误伤 |
| 忌口「牛肉」误伤牛奶（虾仁滑蛋） | 误伤 | 不误伤 |

「羊肉」保留选项：数据里没有任何羊肉食材，挡 0 道属正常。

## B 组：不再偷偷绕过忌口

删掉两处 `safe.length > 0 ? safe : pool` 的静默回退（原 `useAppStore.ts` / `RecipesScreen.tsx`），
改为：

- `filterByAvoid` 结果为空就是空，界面明确提示「这一类都被忌口挡掉了」。
- 菜谱页给「查看全部」按钮：**只临时放宽，不改动已保存的忌口设置**（已验证）。
- 换分类或改忌口时，放宽状态自动作废。

**顺带发现并修掉的同类漏网**（原需求文档没列，但属同一个 bug）：

1. 首页人气榜「最近很受欢迎」不过忌口 → 忌口牛肉后仍显示「芹菜炒牛肉」。
2. 首页大卡片：用户勾上忌口后不换菜，仍显示被忌口的菜（红烧肉含葱姜）。
3. 老用户升级后，已保存的当前菜可能与已保存的忌口冲突 → 加兜底自动换菜。
4. 食材页「能做的菜」不过忌口 → 换个入口又把忌口的菜推荐回来。
5. 修 `filterByAvoid` 返回值改为**新数组**，避免调用方 `sort` 污染 store 里的数组
   （这个坑导致无忌口时首页白屏，已修）。

## C 组：口味偏好整体下线

- `persist` 版本 3 → 4，`migrate` 里清掉老数据里的 `tasteTags` 字段。
- 文案同步：「口味与家庭」→「忌口与家庭」，`ShareSheet` 里的「口味」→「忌口」。
