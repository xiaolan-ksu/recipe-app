## 一、这是什么

家常菜谱 App「今天吃什么」。React Native + Expo SDK 57 + TypeScript，安卓为主，同一套代码也能跑网页版。
原本是纯本地 App。上一轮加了**自建后端的「共享清单」**（两个人共用买菜清单 + 冰箱库存）。
**本轮加了「云更新」**：以后改界面/逻辑不用再重新装安装包，手机自己下载新版；
真动到安卓原生部分时，App 里也能直接把新安装包下下来装。

## 四、共享清单（上一轮）

需求（已确认）：2 个人、都是安卓、双方都能改、**不留操作记录**、不做认领标记、
买回来的东西同步进共享库存、不做推送提醒、用「家庭码」配对、准实时（轮询）。
共享范围只有**买菜清单 + 冰箱库存（含保质期）**；收藏 / 做饭记录 / 口味 / 头像仍留本机。

实现要点：

- 后端：Node 24 + Express + Node 自带的 `node:sqlite`，零额外依赖，数据就一个文件。
- 同步：客户端把每个改动变成一条 op 排队，每 4 秒提交；服务器按**累加**语义合并。
- 断网：改动留在本机队列，联网后按顺序补交。
- 配对：一方创建得到 6 位家庭码（24 小时、一次性）→ 另一方输入加入。
- App 侧文件：`src/lib/share.ts`、`src/lib/useShareSync.ts`、`src/lib/shareStatus.ts`、`src/components/ShareSheet.tsx`；
  store 新增 `shareToken / shareFamilyId / shareRev / shareOutbox / shareSyncedAt`。
- 明文 HTTP：`plugins/withCleartextTraffic.js` 打开安卓的明文开关（云更新也靠它）。

## 五、云更新（本轮新增）

两条路，都用 `expo-updates` + 自建服务器，没走 EAS、没有额外付费服务：

1. **OTA（平时就用这条）**：只改了 JS / 图片 / 文字 / 逻辑 → 打包上传，手机自己下载，
   下次打开就是新版；想立刻生效走「我的 → 版本与更新 → 下载 → 马上重启」。
2. **安装包升级（动了原生才用）**：App 里点一下，把服务器上的新 apk 下到缓存目录，
   拿到 `content://` 交给系统安装器（`expo-intent-launcher`）。需要 `REQUEST_INSTALL_PACKAGES`
   权限，第一次要允许「安装未知应用」。

关键设计：

- **两个版本号分开**（用户 2026-10-13 明确要求）：
  - **版本号** `app.json` 的 `version`：面板上显示的「当前版本」，**每推一次更新都 +1**（9.1.2 → 9.1.3 → …），
    发布脚本自动 +1 并把 `android.versionCode` 对齐成 `大版本×10000 + 中版本×100 + 小版本`（9.1.3 → 90103）。
  - **原生底座** `app.json` 的 `runtimeVersion`：现在是**固定字符串** `"9.1.2"`，构建时写进
    `AndroidManifest.xml` 的 `EXPO_RUNTIME_VERSION`。**只有重打安装包时才改它。**
    绝对不能用 `{policy: appVersion}`——那样它每推一次就跟着涨，老手机就再也收不到 OTA 了
    （发布脚本会直接拦下这种写法）。
  - 客户端判断「要不要重装」看的是原生底座和服务器 `apk/latest.json` 里的 `runtimeVersion` 是否一致。
- 服务器按 [Expo Updates v1 协议](https://docs.expo.dev/technical-specs/expo-updates-1/) 应答，
  用最朴素的 JSON 形式（不带 multipart、不做代码签名）；已是最新时回 **204**，而且必须带
  `expo-protocol-version: 1`，否则客户端会当成错误。
- 更新 ID = `metadata.json` 的 sha256 前 32 位拼成 UUID（跟官方示例服务器一致，客户端要求合法 UUID）。
- 资源 key = 文件内容 md5，正好也是客户端本地保存用的文件名 → 内容没变的资源不会重复下载。
  **每个资源必须带 `fileExtension`**（客户端 `getString` 读不到会直接抛错）。
- 客户端行为是**从 Android 源码里逐条核对过的**（`node_modules/expo-updates/android/src/main/java/...`）：
  它只发 `Expo-Platform / Expo-Runtime-Version / Expo-Protocol-Version / Expo-Current-Update-ID`；
  响应头只认 `expo-protocol-version / expo-manifest-filters / expo-server-defined-headers`；
  `extra.expoClient` 不是必需的（但发了 `Constants.expoConfig` 才有内容）。
- App 侧文件：`src/lib/updates.ts`（检查 / 下载 / 安装）、`src/components/UpdateSheet.tsx`（面板）、
  `src/lib/useAutoUpdate.ts`（后台静默更新）、`ProfileScreen` 里加了「版本与更新」一节。

后台静默更新（2026-10-13 加，9.1.4 修过两个坑）：

- `useAutoUpdate()` 挂在 `App.tsx` 上：挂载时 + 每次回到前台时悄悄
  `checkForUpdateAsync()` + `fetchUpdateAsync()`；不弹窗、不打断。重新查一遍的节流是一小时，
  但**失败过就不等节流**（`retryRef`），下次回前台直接接着试。
- 下好的新版由 expo-updates 在**下次启动 App 时自动用上**（启动选新版本是它自己的机制）。
- **故意不在后台调 `reloadAsync()`**：`expo-updates` 的 `RestartReactAppExtensions.kt` 里
  `ReactHost.restart()` 会先判断 `lifecycleState != RESUMED`，不是前台就先调 `onHostResume(activity)`——
  等于在"后台"状态下把 React 宿主当成前台恢复，真机上会不会出岔子没法在这儿验证，所以不冒这个险。
  想立刻生效走面板上的「马上重启」（用户主动触发，安全）。
- 面板会识别"后台已经下好"这种情况（`Updates.useUpdates().isUpdatePending`），直接提示重启。

**坑 1：检查更新一直转圈（9.1.4 修）**。expo-updates 的检查 / 下载是**排队串行**跑的
（`StateMachineSerialExecutorQueue`）：启动那次正在下 22MB 的新包时，用户在面板里再点检查，
请求会一直排在下载后面——Promise 不 resolve，`phase` 卡在 `checking`，界面就无限转圈。
修法：`runCheck()` 里用 `withTimeout(..., 15000)` 给检查封顶；发现原生侧 `isDownloading` 就不插队，
改成 `backgroundDownload` 状态把进度条显示出来（这个状态不显示转圈、按钮照常可点）。

**坑 2：切到后台下载就停（9.1.4 修）**。安卓在 App 切后台一会儿后会冻结进程，下载自然断
（想真不停就得挂前台服务 + 常驻通知，一个菜谱 App 不值得）。修法：**被打断就接着下**——
切后台时记下 `isDownloading`，回来时若确实在下载且离开超过 10 秒，就带 `force` 再跑一次
`fetchUpdateAsync()`。能"接着下"是因为 expo-updates 每个资源都按**内容 md5** 存盘、
下次发现文件已在就直接跳过（`FileDownloader.kt` 里 `if (path.exists())` 那段），
所以已经下好的图片不会重来。

## 七、云更新怎么发（每次改完就干这个）

```powershell
# 平时（只改 JS）：脚本自己把版本号 +1，然后打包上传校验
node work\publish-update.mjs --note "这次改了什么"

# 动了原生：先把 app.json 的 version 和 runtimeVersion 一起改新号（versionCode 跟着改），
# prebuild → 打包装 APK，然后只传安装包
node work\publish-update.mjs --apk-only --note "..." --apk "<apk 路径>"
```

脚本默认对**自己的项目根目录**（`<项目根目录>`）操作——版本号 +1 写在它的 app.json 里。
脚本会：版本号 +1 → 打包 JS →（可选）传安装包 → scp 上传 → **模拟手机问一次服务器，把每个文件下一个遍核对哈希**。
校验不过会直接报错，不会留下坏版本。`--no-bump` 可以跳过 +1。

## 九、构建环境的坑（重新打包必须知道）

1. 沙箱里 JVM 的 AF_UNIX 自管道连不上 → `JAVA_TOOL_OPTIONS=-Djdk.net.unixdomain.tmpdir=<不存在的目录>`。
2. 用户名含中文 → `TEMP`/`TMP` 必须指向 `<临时目录>`（AGP 生成的 .bat 会被 cmd 按 GBK 误读）。
3. pnpm 11 不再从 `.npmrc` 读 `node-linker` → 要写在 `pnpm-workspace.yaml`（`nodeLinker: hoisted`）；
   源码目录也补上了这个文件，否则原生模块落在 `.pnpm` 超长路径下，CMake 会报「对象路径超 250 字符」。
4. **Metaspace 512M 不够了**：加了 expo-updates / expo-intent-launcher 两个原生模块后，
   守护进程会卡在刷 `OutOfMemoryError: Metaspace`（CPU 空转，不报错也不结束）。
   已把 `android\gradle.properties` 改成 `-Xmx2560m -XX:MaxMetaspaceSize=1024m`，
   `build-apk.bat` 里也带了同样的 `-Dorg.gradle.jvmargs`（prebuild --clean 会冲掉前者）。
   构建像是卡住时先 `Get-Process java` 看一眼，杀掉旧守护进程再重来。
5. `pnpm exec expo install <包>` 在这台机器上出现过**只装进 node_modules、不写 package.json / lockfile**，
   表现是「包里明明有，构建却找不到」。装完一定用 `pnpm list <包>` 和 `Select-String pnpm-lock.yaml` 各验一次。
6. 以上都已固化在 `<项目根目录>\build-apk.bat`，打包只要 `cmd /c <项目根目录>\build-apk.bat`。
7. 完整流程（源码与构建目录已合并，**不再需要 robocopy 同步**）：
   在 `<项目根目录>` 下 → `node node_modules\@expo\cli\build\bin\cli prebuild --platform android --clean --no-install`
   → 重建 `android\local.properties`（内容 `sdk.dir=D\:\\android-sdk`）→ 跑 `<项目根目录>\build-apk.bat`。
8. 构建链：JDK 17（`D:\gradle-home\jdks\...`）、Gradle 9.3.1、AGP 8.12.0、compileSdk/targetSdk 36、minSdk 24。
9. 这台机器 `npx` 不在 PATH 上，直接用 `node node_modules\@expo\cli\build\bin\cli <命令>` 更稳。
